## 0. 给 Codex 的最高优先级执行指令

你现在是本项目的全栈开发者。**请直接创建并维护真实、可运行的项目代码，而不是只输出方案、伪代码、静态页面或待办事项。**

1. 先检查当前仓库，不得随意覆盖或删除用户已有代码。若仓库为空，则从零搭建；若存在代码，则尽量兼容并增量实现。

3. 管理员**不需要注册**，不得实现公开注册页面、`/register` 接口或“注册管理员”入口。首次初始化管理员账号为 `ljm`，初始密码为 `Ljm123`。
4. 前端使用 **Vue 3**，后端使用 **FastAPI**；浏览器以**同源 `/api`** 访问后端，便于 CloudStudio 部署。开发环境 Vite 代理，部署环境采用反向代理；不得把 `localhost:8000` 之类的后端绝对地址写死在浏览器代码中。

7. 如果运行环境缺少依赖，可以创建安装脚本和清晰命令，不能把“未运行”写成“已通过”。
8. 最终仓库需提供 `README.md`、`.env.example`、数据库初始化方式、CloudStudio 运行步骤、初始登录说明、测试命令及已知限制。

11. **新增硬性 UI 需求：后台多标签页导航**。必须按第 3.3 节实现「左侧菜单打开标签 → 右侧顶部标签栏保留多个页面 → 点击标签立即切换 → 可关闭标签」，而非仅实现传统单页面菜单切换。管理员端与普通员工端均使用各自独立的标签栏；第一阶段就要完成标签栏基础行为，不得推迟到最后优化。

## 1. 总体技术方案（工程细化）

### 1.1 技术选型

| 层次 | 方案 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 单页应用，组件化实现 |
| UI | Element Plus | 表单、表格、对话框、导航等 |
| 图表 | Apache ECharts | 饼图、柱状图、趋势图 |
| 路由与状态 | Vue Router + Pinia | 路由守卫和登录用户状态 |
| HTTP | Axios | 统一 `/api` 前缀、错误处理和 CSRF 头 |
| 后端 | Python + FastAPI + Pydantic v2 | REST API、输入校验和 OpenAPI 文档 |
| ORM 与迁移 | SQLAlchemy 2.x + Alembic | 建表、迁移、数据约束 |
| 数据库 | SQLite（首版） | 适合约 30 人的小型系统；路径配置化，数据持久化 |
| Excel | openpyxl | 真实生成 `.xlsx` 文件 |
| 密码 | Argon2id 哈希（例如 `pwdlib`） | 禁止明文保存/返回密码 |
| 测试 | pytest + FastAPI TestClient/httpx；前端构建检查 | 覆盖重要业务及权限 |
| 部署 | CloudStudio + 同源反向代理 | 单一可访问端口，前端 `/`、后端 `/api/` |

不要为首版引入 Redis、Celery、Kafka、Kubernetes 或多租户系统。除非现有仓库已经使用兼容方案，否则遵循上述选型。

### 1.2 架构和访问路径

```text
浏览器
  └── http(s)://<CloudStudio-预览地址>/
      ├── /                  → Vue 构建后的静态页面
      └── /api/*             → 同源反向代理 → FastAPI
                                        └── SQLAlchemy → SQLite 持久化文件
```

开发环境：Vue Vite 开发服务器将 `/api` 代理到 FastAPI；生产/CloudStudio 部署：优先使用 Nginx 等反向代理在同一端口托管前端和转发后端。如果 CloudStudio 无法安装反向代理，可提供“FastAPI 同源托管构建后前端”的**明确标记的降级方案**，但默认交付仍包含反向代理配置。

### 1.4 通用约定

- 所有业务 API 位于 `/api` 下；Swagger 文档建议在 `/api/docs`（具体 URL 需与反向代理配置保持一致）。
- JSON 使用 UTF-8；前后端字段统一使用英文 `snake_case`（后端）或在前端显式转换，不允许同一业务字段随意混用命名风格。
- 业务时间以 `Asia/Shanghai` 为默认时区；数据库内部时间戳统一存 UTC，前端本地化显示。只涉及自然日的日期字段使用 `YYYY-MM-DD`。
- 列表默认分页（`page=1&page_size=10`，最多 100），支持搜索、筛选和加载/空数据/错误状态。
- 业务编号例如员工 `MS0001`、任务 `TASK0001`，实际流水由数据库事务保障唯一，不能以“当前行数 + 1”生成。
- 所有写操作校验权限和数据有效性；禁止只有前端隐藏按钮而后端不授权。
- 删除操作必须二次确认；存在历史业务关联时优先停用/归档而非物理级联删除。

## 2. 用户、认证和权限

### 2.1 管理员登录（原 Word 明确要求）

**取消管理员注册。** 系统首次初始化时，若数据库尚无管理员账号，创建：

```text
用户名：ljm
初始密码：Ljm123
角色：ADMIN
```

**必须实现**：

1. 登录页包含用户名、密码和登录按钮；可点击“显示/隐藏密码”。
2. 正确登录后进入管理员首页 `/admin/dashboard`；错误时显示通用错误提示“用户名或密码错误”，避免泄露账号是否存在。
3. 登录后刷新页面仍保持登录，直到会话超时或用户退出；退出后回登录页并使旧会话失效。
4. 管理员在系统设置中输入旧密码、新密码、确认新密码以修改密码；改密后能用新密码登录。
5. 首次启动**只初始化一次**；重启服务不得把已修改的密码重置成 `Ljm123`。
6. **绝对禁止公开注册管理员的路由、API 或按钮。**

**关于文档中的密码规则（工程细化）**：原 Word 保留了“新密码必须满足注册时的密码规则”的说法，但注册环节已删除。因此采用之前沟通的复杂度规则：新密码 **8～10 位**，并且同时包含**大写字母、小写字母、数字**。初始管理员密码 `Ljm123` 只有 6 位，属于用户指定的**初始化例外**，不能因不满足“新密码”规则而导致初始账号登录失败。生产环境应尽快修改该公开初始密码；登录页可提示“首次部署请修改初始密码”。用户名新建时最长 10 个字符（员工账号使用自动生成的简短编号）。

### 2.2 普通员工账号

- 只有管理员能创建/启用普通员工账号，普通员工不能注册。
- 新增员工时支持“同时创建登录账号”，初始用户名建议使用该员工的唯一员工编号（如 `MS0001`）；管理员设置满足新密码规则的初始密码。
- 若员工已有资料但尚未启用账号，管理员可以在员工详情中启用账号；不得为同一员工创建多个有效账号。
- 普通员工登录后进入 `/employee/profile` 或 `/employee/dashboard`（首版可以直接进入个人信息页）。
- 员工离职时禁用对应登录账号，但保留员工信息和历史数据；允许管理员在合理校验后重置在职员工密码。

### 2.3 会话及安全设计（工程细化）

- 使用**数据库持久化的服务端会话**：浏览器仅通过 `HttpOnly` Cookie 持有随机不可预测的会话标识；数据库仅保存会话标识的哈希，记录用户、过期时间及撤销状态。
- Cookie：`HttpOnly`、`SameSite=Lax`、`Path=/`，HTTPS 正式部署启用 `Secure`；纯 HTTP 本地/CloudStudio 预览可通过环境变量关闭 `Secure`，并在文档中提示仅用于开发演示。
- 会话有效期默认 8 小时（可配置）；用户主动退出立即撤销会话。刷新页面通过 `GET /api/auth/me` 恢复登录，无需重新输入密码。
- 对所有已认证的 POST/PUT/PATCH/DELETE 操作校验 `Origin`/允许来源，配合会话绑定的 CSRF Token（由登录/`me` 响应返回，浏览器在 `X-CSRF-Token` 头中提交）；登录接口也要校验来源并只接受 JSON。
- 前端请求启用 `withCredentials`；生产不启用通配符跨域 CORS，不在 `localStorage` / `sessionStorage` 存放密码或认证密钥。
- 密码使用 Argon2id 哈希；限制登录失败频率，至少针对用户名/IP 做基础节流。初始密码仅在初始化/文档中出现，不记录到运行日志。
- 禁止从客户端传 `role=ADMIN` 或 `employee_id` 就获得其他人的数据；后端每次根据会话的用户身份鉴权。

## 3. 页面设计与菜单

### 3.1 管理员端

采用经典管理后台结构：固定左侧导航栏 + 顶部系统名称/用户名/退出登录 + **右侧顶部工作区多标签栏 + 右侧当前激活页面内容**。浏览器适配电脑显示，界面中文、清晰、不花哨。**不能省略多标签栏，把它仅做成面包屑或当前模块标题。**

**左侧菜单必须且仅需按以下 9 个一级模块组织**：

| 序号 | 菜单名 | 建议路由 | 主要页面 |
|---|---|---|---|
| 1 | 首页概览 | `/admin/dashboard` | 数据卡片、饼图、7 日柱状图 |
| 2 | 员工信息管理 | `/admin/employees` | 员工列表、详情、新增、编辑、离职、导出 |
| 3 | 部门与岗位管理 | `/admin/departments` | 部门/岗位管理 |
| 4 | 考勤管理 | `/admin/attendance` | 考勤录入、筛选、月度统计、导出 |
| 5 | 请假审批 | `/admin/leaves` | 待审批及历史记录、通过/驳回 |
| 6 | 薪资管理 | `/admin/payroll` | 工资草稿、编辑、发放状态、导出 |
| 7 | 制琴任务管理 | `/admin/tasks` | 生产任务、进度、人员分配、质检 |
| 8 | 统计报表 | `/admin/reports` | 部门、考勤、薪资支出、任务统计 |
| 9 | 系统设置 | `/admin/settings` | 账号资料、修改密码、企业信息、退出 |

页面公用交互：表格分页、关键字搜索、状态筛选、表单校验、必填提示、提交 loading、成功/失败反馈、确认弹窗、无数据展示。绝不出现点击无响应的假按钮。

### 3.2 普通员工端

普通员工登录后显示独立布局和以下 6 个页面/菜单：

| 菜单 | 建议路由 | 功能 |
|---|---|---|
| 个人信息 | `/employee/profile` | 查看个人资料，修改允许的联系方式 |
| 个人考勤 | `/employee/attendance` | 查看本人每日考勤及月度统计 |
| 请假申请 | `/employee/leaves` | 申请、查询结果、撤销待审批申请 |
| 我的工资 | `/employee/payroll` | 查看本人月度工资和发放状态 |
| 我的任务 | `/employee/tasks` | 查看本人参与的制琴任务和进度 |
| 账号设置 | `/employee/settings` | 修改密码、退出登录 |

`/login` 对所有身份统一。登录后由后端用户角色决定跳转地址；访问无权限路由应跳转到自己有权访问的首页或显示 403。刷新任意页面路由要正常工作。

### 3.3 新增必做：后台多标签页导航（Multi-Tab Navigation，工程补充需求）

> **用户新增需求（优先级：必须实现）**：参照浏览器页签的交互习惯，在**后台网页内部**加入多标签页工作区。点击左侧菜单打开模块后，右侧上方出现对应的可点击标签；此后可在顶部不同模块标签之间直接切换，无需反复点击左侧菜单。**这不是让浏览器新建 Chrome 标签页，而是单个 Vue SPA 内部的可切换工作区标签栏。**

#### A. 布局结构

管理员端和普通员工端均采用以下结构，其中菜单仍分别按第 3.1 节的九项和第 3.2 节的六项设置：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 满氏吉他制琴有限公司企业员工管理系统               当前用户 / 退出登录 │
├────────────────┬────────────────────────────────────────────────────────┤
│                │ [首页概览] [员工信息管理 ×] [薪资管理 ×] [制琴任务 ×]  │
│ 左侧菜单栏     ├────────────────────────────────────────────────────────┤
│                │                                                        │
│ 首页概览       │      当前激活的标签页内容（如：薪资管理）              │
│ 员工信息管理   │                                                        │
│ 部门岗位管理   │      表格 / 搜索 / 编辑 / 图表 / 业务操作              │
│ 考勤管理       │                                                        │
│ 请假审批       │                                                        │
│ 薪资管理       │                                                        │
│ 制琴任务管理   │                                                        │
│ 统计报表       │                                                        │
│ 系统设置       │                                                        │
└────────────────┴────────────────────────────────────────────────────────┘
```

- **位置**：右侧主工作区最上方（全局顶栏下方、业务内容上方）是一整行工作区标签；标签名称与模块中文菜单名称一致。
- **视觉**：选中标签有明显高亮/底边框或卡片选中态；未选中标签仍可读；可关闭的标签右侧有 `×`，鼠标悬停时突出显示关闭操作。
- **响应**：适配 1366×768 的桌面窗口；标签数量超过可用宽度时，标签栏**水平滚动**或出现“更多标签”下拉，不能把整个主区域挤到不可用，也不能换成多行遮挡业务内容。
- **内容区**：标签栏下方只显示**当前激活**页面；切换页签时不新建浏览器标签、不整页刷新、不重置身份或丢失其他页签。

#### B. 必须实现的交互行为（不可只做视觉演示）

1. **左侧菜单打开页签**：点击“员工信息管理”后，右侧标签栏新增 `员工信息管理 ×` 并显示员工页面；随后点击“薪资管理”新增 `薪资管理 ×`。两个标签同时存在。
2. **顶部直接切换**：点击已打开的“员工信息管理”标签，立即切回员工页面；点击“薪资管理”可再切回，**不用再次点击左侧菜单**。
3. **禁止重复标签**：同一路由的菜单重复点击不会生成第二个相同标签，只激活已有标签。
4. **同步选中状态**：切换标签后，对应的左侧菜单项同步高亮；面包屑（如有）、页面标题和浏览器 URL 均应与当前标签一致。
5. **支持关闭**：普通业务页签右侧提供 `×` 关闭按钮。关闭非当前页签不影响当前页面；关闭当前页签后优先激活其左侧相邻标签，如不存在则激活右侧相邻标签，最后回到角色默认首页。
6. **默认首页**：管理员登录后默认打开 `首页概览`，员工登录后默认打开 `个人信息`。建议该首页标签**常驻且不可关闭**，其余标签可关闭，以防工作区出现没有页面的空状态。
7. **浏览器前进/后退**：通过 Vue Router 路由切换（例如 `router.push` / `router.replace`），使浏览器前进、后退按钮与活动标签同步；不得只改变按钮颜色而页面或 URL 未变化。
8. **刷新页面恢复**：浏览器刷新时，当前有效路由应直接正常渲染，不必重新登录；对于已打开的多个标签，使用 `sessionStorage` 在**同一浏览器页签会话**中恢复其名称、顺序及活动状态。若持久化信息缺失/损坏，优雅降级为默认首页加当前可访问页面。
9. **权限隔离**：只有管理员才能打开 `/admin/**` 的标签，员工只允许 `/employee/**`；登录页、403 页、未知路由以及非菜单权限路由不得作为可用业务页签添加。后端仍负责实际 API 授权。
10. **退出后清理**：用户退出登录、会话失效或切换不同账号时，清除上个账号的工作区标签缓存；不得让下一个账号继承管理员标签或上一员工个人业务页面。
11. **打开过的页面保留状态**：普通标签间切换时，优先使用 Vue `KeepAlive` 缓存已打开页面，尽量保留列表筛选、当前页码、滚动位置和未提交的普通输入。关闭标签时销毁相应缓存；若页面涉及工资、员工隐私等敏感数据，退出/失效时必须清理对应缓存。业务写入后根据实际情况重新查询后端，不可以缓存旧数据冒充最新结果。
12. **关闭未保存编辑**：对存在未提交修改的编辑表单，关闭标签时应显示“当前页面有未保存的修改，确定关闭吗？”；确认后关闭，取消则保留。可以通过页面统一的 `dirty` 状态接口实现；如果表单是弹窗/抽屉，也要保证关闭标签不会静默丢弃正在输入的重要信息。
13. **标签操作范围**：不需要为每一行“员工详情”单独新增标签；首版的标签粒度对应左侧一级菜单页面（九个管理员模块和六个员工模块）。详情、新增、编辑继续采用现有表单/弹窗/抽屉实现。

#### C. 具体示例：用户期望的体验

```text
登录管理员 → 默认标签：[首页概览]
点左侧“员工信息管理” → [首页概览] [员工信息管理 ×]  （员工页面激活）
点左侧“薪资管理” → [首页概览] [员工信息管理 ×] [薪资管理 ×]  （薪资页面激活）
点上方“员工信息管理” → 不操作左侧菜单，员工页面立即激活
再次点左侧“员工信息管理” → 仍只有一个员工管理标签
点“薪资管理 ×”关闭 → 薪资标签消失，不影响员工页面
刷新网页 → 标签栏与当前激活页面恢复，仍维持正常登录
退出登录 → 清除标签缓存；再次登录按当前账号角色重新初始化
```

#### D. 推荐技术实现（Vue 3 + Element Plus）

- 使用 `Vue Router` 管理业务 URL，`Pinia` 创建独立的 `tabsStore`（或 `workspaceTabsStore`）；可以使用 `Element Plus` 的 `el-tabs`，`type="card"` 或自定义标签容器，要求交互行为一致。
- 为菜单路由设置稳定的 `route.meta.title`、`route.meta.role`、`route.meta.affix`（默认首页为常驻）和可选 `route.meta.keepAlive`；仅允许**预定义、符合当前角色权限**的业务菜单路由进入标签栏。
- `tabsStore` 至少包含 `tabs`（`[{path, title, closable}]`）和 `activePath`，实现 `openTab(path)`、`activateTab(path)`、`closeTab(path)`、`restoreTabs()`、`resetTabs()`；对标签统一使用**规范化路由 path** 作为唯一键，防止重复。
- 路由守卫中校验身份、角色并同步标签；`router.push(path)` 后由路由变更更新活动标签，不要让路由和 `activePath` 长期不一致，也不要造成无限重定向。
- 用 `sessionStorage` 只保存**无敏感信息的菜单 path、打开顺序和当前标签 path**，禁止保存密码、Cookie、CSRF token、员工/工资记录或整个页面组件状态。恢复时须重新通过 `/api/auth/me` 验证会话和角色，再对持久化的每个 path 重新执行路由白名单校验。按照登录用户 ID + 角色隔离存储键，或在用户登出时全量清理。
- 若启用 `KeepAlive`，通过 `router-view` 插槽缓存业务组件，处理标签关闭后的缓存释放；敏感数据不应跨用户会话保留；从其他页面返回时合理刷新必要的后台统计数据。
- 建议提供 `WorkspaceTabs.vue`（可复用）、`stores/tabs.ts`、菜单/路由配置，**尽量共享一套标签逻辑**，管理员和普通员工通过各自的许可路由列表隔离。
- **不用新增后端接口或数据库表**支持标签栏；这是前端导航功能。任何后端数据仍由原业务 API 提供。

#### E. 标签页 UI 的单独验收判定

**必须实际在浏览器中操作验证**：一次登录后可先后打开至少三个不同功能模块，顶部同时显示三个页签，顶部切换无需侧栏，重复打开无重复标签，关闭与路由/侧栏同步，刷新后恢复；管理员和员工互不串标签。**若 Codex 只交付“左侧菜单点击后切换右侧内容区”，即使其他模块可用，也判定此新增 UI 需求未完成。**

### 5.1 字段

| 字段（API） | 规则 | 说明 |
|---|---|---|
| `employee_code` | 自动生成、唯一、只读 | 如 `MS0001` |
| `name` | 必填，1～50 字符 | 员工姓名 |
| `gender` | 选填 | 男/女/其他/未填写 |
| `birth_date` | 选填，日期 | 选择出生日期（年龄自动计算，不重复存储年龄） |
| `phone` | 必填 | 基础手机号格式校验，允许保存中国大陆常用 11 位号 |

**校验**：部门/岗位必须匹配；员工必须属于有效部门；同一个员工不能重复创建多个登录账号；修改基本工资不追溯修改已经生成的历史工资单。

## 7. 员工考勤管理

### 7.1 考勤字段与状态

每条记录：员工编号、姓名（关联显示）、考勤日期、上班时间、下班时间、考勤状态。

`status` 枚举：

| 内部值 | 页面显示 |
|---|---|
| `normal` | 正常 |
| `late` | 迟到 |
| `early_leave` | 早退 |
| `absent` | 缺勤 |
| `leave` | 请假 |

### 7.2 功能与规则

1. 管理员按员工和日期手动新增/修改考勤，支持按日期、月份、姓名、部门、状态检索。
2. 数据库对 `(employee_id, attendance_date)` 建立联合唯一约束，防止同员工同日重复记录；重复插入返回明确错误，而不是生成重复数据。
3. 可查看按员工、月份计算的正常天数、迟到次数、早退次数、缺勤天数、请假天数，并导出月度 `.xlsx`。
4. `clock_in`/`clock_out` 为选填时间；如果两者都填写，需校验下班时间不早于上班时间（首版按同日上下班处理）。
5. **不自动把“缺少考勤记录”视为缺勤**：首版没有排班及法定假日表，缺勤需要管理员主动标记。
6. 经审批产生的 `leave` 考勤记录不允许普通员工自行改动。管理员如需修改冲突的考勤，必须先处理请假业务；系统提示冲突，不得静默覆盖。
7. 首版无需人脸/指纹设备、移动定位打卡或自动排班。

## 8. 员工请假与审批

### 8.1 请假信息

- 申请人关联员工账号，不能由员工替他人提交。
- 请假类型：`personal` 事假、`sick` 病假、`annual` 年假。
- 开始日期、结束日期、请假原因（必填）。
- 申请状态：`pending` 待审批、`approved` 已通过、`rejected` 已驳回；工程上可增加 `cancelled` 已撤销，用于员工撤销未审批申请。
- 审批时间、审批人、驳回原因（驳回时建议必填）。

> **工程边界**：原文使用“开始时间/结束时间”；首版按**整天请假**实现，使用开始/结束日期（包含首尾日期），不支持小时/半天或节假日专项规则。默认周一至周五为工作日，周末不生成请假考勤。若后续需要细化时间或调休，另行升级。

### 8.2 业务流程

1. 员工在自己的请假页面提交申请，且 `end_date >= start_date`，日期范围至少覆盖一个工作日。
2. 待审批申请可由**该员工自己**撤销，已通过或已驳回不可撤销。
3. 管理员可查看全部申请并按员工、日期、状态筛选，可通过/驳回待审批申请；不允许重复审批。
4. 审批通过时，在**同一数据库事务**中将对应工作日的考勤设置为 `leave`（已有记录按明确的业务规则更新），以免审批成功但考勤未更新。
5. 为避免覆盖管理员原有考勤数据：若请假区间存在已记录的非请假考勤，接口应返回冲突提示，管理员先核对并处理后再审批；整个审批事务不得部分成功。若存在重叠的其他已批准请假，也需拒绝冲突。
6. 请假已通过时，同一员工同日仅能有一条请假考勤；月度统计和今日请假人数均不能重复计数。
7. 员工只能查询本人的申请及结果，管理员可查询全部。

## 9. 员工薪资管理

### 9.1 月度工资结构

| 字段 | 规则 |
|---|---|
| 员工 | 关联员工，显示编号/姓名/部门 |
| 月份 | `YYYY-MM` |
| 基本工资 | 当月生成时从员工档案复制一份快照 |
| 奖金 | 默认 0，管理员可调整，非负 |
| 扣款 | 默认 0，管理员可调整，非负 |
| 实发工资 | **基本工资 + 奖金 - 扣款**，由后端计算 |
| 发放状态 | `unpaid` 未发放 / `paid` 已发放 |
| 发放时间 | 标记已发放时记录，允许为空 |

**必须实现**：

1. 管理员选择月份，按当前在职员工批量生成当月工资草稿。
2. 同一员工、同一月份只能有一份工资记录，数据库联合唯一约束 `(employee_id, salary_month)`；再次执行生成时**跳过已有记录**，绝不覆盖奖金/扣款/发放状态。
3. 管理员可编辑未发放工资的奖金和扣款，后端重新计算实发工资；**不允许由浏览器提交并覆盖实发工资**。
4. 如果按公式结果为负数，拒绝保存并提示检查扣款金额。
5. 已发放工资不能被普通编辑流程更改；管理员需先通过明确的“撤回已发放状态”（二次确认）才能修改，操作可以留下审计记录。
6. 按月份、姓名、部门查询，支持导出 `.xlsx`；只有管理员可导出全公司工资。
7. 员工只能查看自己的工资明细及发放状态。
8. 所有金额在服务端用**分的整数**存储或使用 `Decimal` 严格处理，向浏览器统一输出两位小数，禁止用 JS/Python 浮点直接累计金额。
9. 首版不自动计算个人所得税、社保、法定假期或考勤扣款；扣款由管理员手动录入。

## 10. 吉他制琴任务管理（必须保留的企业特色）

### 10.1 创建任务

| 字段 | 约束 |
|---|---|
| `task_code` | 自动生成、唯一 |
| `name` | 任务名称，必填 |
| `guitar_model` | 吉他型号，必填 |
| `planned_quantity` | 生产数量，正整数 |
| `completed_quantity` | 已完成制作数量，0～计划数量，默认 0 |
| `owner_employee_id` | 负责人，必须为在职员工 |
| `participant_ids` | 参与员工 ID 列表，支持多人，不重复 |
| `start_date` | 开始日期，必填 |
| `due_date` | 预计完成日期，不早于开始日期 |
| `priority` | `low`/`medium`/`high`（低/中/高） |
| `notes` | 任务备注，选填 |
| `status` | `not_started`/`in_progress`/`pending_qc`/`completed` |

展示示例：**“MS-01民谣吉他生产任务”，计划制作 5 把**。示例不是自动创建的真实业务数据。

### 10.2 任务流程

```text
待开始 → 制作中 → 待质检 → [质检通过] → 已完成
                   └── [质检不通过] → 制作中
```

- 管理员可新建/编辑任务、指定负责人和多名参与员工、推进状态、录入 `completed_quantity`，并查询状态、负责人、吉他型号。
- 列表显示 `completed_quantity / planned_quantity`、进度条、计划完成日期、负责人和状态。
- 只有 `completed_quantity == planned_quantity` 的任务才允许进入“待质检”；只有待质检且最新质检通过的任务才能标为“已完成”。
- 质检记录包含任务、结果（通过/不通过）、备注、操作管理员、质检时间；不通过退回“制作中”，保留质检历史。
- 已完成任务只读保留，作为历史记录；任务详情可以查看所有参与员工和历次质检结果。
- 普通员工只能查看自己是负责人或参与人的任务，不得修改状态、数量、分配及质检结果。
- 已离职员工可以保留在历史任务关联中，但不允许被新增分配到当前任务。
- 首版不开发原材料库存、设备维修、复杂销售订单或生产排程。

## 12. 数据库表设计（工程细化；Codex 应生成 ORM 模型和迁移）

建议至少使用以下表。字段均具有常规的 `id` 主键、必要的 `created_at`/`updated_at`，外键保持完整性，索引根据检索字段建立。敏感信息不要放在日志。

| 表 | 关键字段 | 约束/关系 |
|---|---|---|
| `users` | `id`, `username`, `password_hash`, `role`, `employee_id`, `is_active` | 用户名唯一；`role` 为 `ADMIN` / `EMPLOYEE`；员工账号对应单个员工 |
| `sessions` | `id`, `token_hash`, `user_id`, `csrf_token_hash` 或等价值, `expires_at`, `revoked_at` | 会话可撤销/过期；令牌哈希唯一 |
| `departments` | `id`, `department_code`, `name`, `description`, `is_active` | 编号、名称唯一 |
| `positions` | `id`, `department_id`, `name`, `description` | `(department_id, name)` 唯一 |
| `employees` | `id`, `employee_code`, `name`, `gender`, `birth_date`, `phone`, `hire_date`, `department_id`, `position_id`, `base_salary_cents`, `status`, `departure_date` | 编号唯一；关联部门/岗位 |
| `attendance_records` | `id`, `employee_id`, `attendance_date`, `clock_in`, `clock_out`, `status`, `source` | `(employee_id, attendance_date)` 唯一；`source=manual/leave` |
| `leave_requests` | `id`, `employee_id`, `leave_type`, `start_date`, `end_date`, `reason`, `status`, `reviewer_user_id`, `reviewed_at`, `rejection_reason` | 关联员工及审批用户 |
| `payroll_records` | `id`, `employee_id`, `salary_month`, `base_salary_cents`, `bonus_cents`, `deduction_cents`, `net_salary_cents`, `status`, `paid_at` | `(employee_id, salary_month)` 唯一 |
| `production_tasks` | `id`, `task_code`, `name`, `guitar_model`, `planned_quantity`, `completed_quantity`, `owner_employee_id`, `start_date`, `due_date`, `priority`, `status`, `notes` | 任务编号唯一；负责人外键 |
| `production_task_members` | `id`, `task_id`, `employee_id` | `(task_id, employee_id)` 唯一，支持多人 |
| `quality_inspections` | `id`, `task_id`, `result`, `notes`, `inspector_user_id`, `inspected_at` | 任务可多次质检，历史不可覆盖 |
| `audit_logs`（建议） | `id`, `actor_user_id`, `action`, `target_type`, `target_id`, `created_at`, `summary` | 记录工资发放状态变更、请假审批和账号重置等关键操作；不存密码 |

**实现约束**：

- `users.employee_id` 建立唯一约束（允许管理员为 `NULL`）。
- SQLite 开启外键约束（`PRAGMA foreign_keys=ON`）；数据模型不要假设 SQLite 默认强制外键。
- 部门、岗位被员工引用时不能直接删除；离职只改状态。
- 历史工资使用生成时基本工资快照，不随当前 `employees.base_salary_cents` 更新。
- 会话数据及业务数据库均需在 CloudStudio 可持久化目录中；绝不能使用每次运行就重新创建的内存数据库保存真实数据。
- Alembic 迁移或等价初始化过程必须可重复执行；重启不能产生重复部门和初始管理员。

## 13. REST API 设计（工程细化）

```json
{"code": "VALIDATION_ERROR", "message": "请检查输入内容", "details": {}}
```

```json
{"items": [], "total": 0, "page": 1, "page_size": 10}
```

| DEP-01 | 删除有员工关联的部门/岗位 | 返回冲突或校验失败，数据未被删除 |
| ATT-01 | 同一员工同日两条考勤 | 数据库唯一约束生效，不允许重复 |
| ATT-02 | 按月汇总考勤 | 正常/迟到/早退/缺勤/请假各状态数量正确 |
| LEAVE-01 | 员工申请 → 管理员通过 | 状态变更，涉及工作日生成请假考勤 |
| LEAVE-02 | 非本人撤销申请或重复审批 | 返回 403/409，不能越权或重复审批 |
| LEAVE-03 | 请假与已有考勤冲突 | 审批事务回滚，向用户解释冲突 |
| PAY-01 | 月度工资生成两次 | 同一员工同月仅一条，已有奖金等字段不丢失 |
| PAY-02 | 修改奖金和扣款 | `实发 = 基本 + 奖金 - 扣款` 严格正确 |
| PAY-03 | 员工尝试访问其他人工资 | 返回 403/404 或根本无法取得目标记录 |
| TASK-01 | 新建 5 把吉他任务并分配多人 | 负责人和参与关系准确保存 |
| TASK-02 | 质检不通过 / 通过 | 失败退回制作中；通过后才允许完成 |
| TASK-03 | 员工尝试修改任务或查看不参与的任务 | 后端阻止越权 |
